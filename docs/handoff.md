# Handoff: where QuakeOG stands

## On the board today
- **Demo player** (apps/qogdemo): flashed and playing Quake demo 1 on the FREE-WILi OG at 3 to 7 fps, from agent-o. It uses a 1-byte depth buffer.
- **E1M1 fly-through** (apps/qogfly): ran at 6 to 9 fps before the demo player replaced it.
- **Benchmark** (apps/qogbench): 52.5 ms per 320x152 lit view before the speed-ups.

## The full game, split across both RP2040s
- Server on the main chip (quake_main), client on the display chip (quake_display), joined by the link driver. Exact on the PC (state hashes, saves and frames identical to the single-process game).
- quake_main links (about 1.7 KB RAM spare). quake_display links for E1M1 only (68 KB hunk, 34 KB stack, about 1 KB spare), using the 1-byte depth buffer the user approved for the board client only.
- Fast spans (Agent AH, not run on hardware): the Fast drawer does no float work per span (64-bit fixed point starts, one integer divide per sub-span end, `QOG_RFAST_FIX`) and its pixel loop reads texel addresses and light rows from the SIO interpolators (`QOG_LITSPAN_INTERP`, checked once at start-up). The board client's console is 1 KB, and its hunk is 3 KB smaller than `QOG_CL_HUNK_KB` says (`QOG_BOARD_CONSMALL`), so the configure line stays as it is. A PC model of the XIP cache (`QOG_XIPSIM`) puts the spans' data misses at about 2,100 a view, so no RAM went to texture or colour map buffers (docs/changes.md).
- Turbo render mode (Agent AO, not run on hardware): Options, Render cycles Exact, Fast and Turbo (`r_fast` 0, 1, 2). Turbo draws the 3D view at 160x152 with the Fast shortcuts, packed at the start of the frame buffer, and core 1's scanout sends each pixel twice (`QOG_BOARD_TURBO`, on). 2D over the view spreads it to full width first. The edge and vertex caches go where a Turbo frame's scanout never reads, so the race wait goes. Exact and Fast are byte identical, the Benchmark says `render Turbo` (docs/changes.md).
- Fast and Turbo spans in Thumb in RAM (Agent AR, not run on hardware): a power-of-two lit surface's spans start from 32-bit sums, their sub-spans, light runs and pixels run in hand-written Thumb, the z run loop in RAM (`QOG_BOARD_LITQ`, checked against the C at start-up, each core's copy of d_scanlit.c with its own state), the z is written by the pixel loop, and light runs share their ends (`QOG_BOARD_LITQSHARE`). Turbo draws model triangles within 3 x 3 pixels without gradients (`QOG_BOARD_TURBOTINY`). An emulator replay of demo3's surfaces through the board's code puts the spans at 35% fewer cycles in Fast and 39% in Turbo. AS's board model predicts demo3 Fast 25.3 fps and Turbo 29.0 at 300 MHz (main 22.6 and 26.5). Exact is byte identical, the display keeps 364 B beside the heap reserve (docs/changes.md).

- Two-core surface pipeline (Agent AM, not run on hardware): core 1 draws whole lit world surfaces while core 0 scans the edges, both share each flush's surfaces, exact in both render modes (`QOG_BOARD_DRAWCORE1`, on). Estimated 9 to 13 ms off a demo3 view. The `[time cl] core1` line shows core 1's busy and idle time, docs/changes.md says how to read it.
- Client hunk (Agent AD): 75 KB now covers every level of the game on a fight tour (worst e2m6 71.2 KB and e4m5 71.0 KB, episode 1 67.0), from exact cuts (docs/changes.md). Every changelevel used to stop the board client (receive buffer in the z-buffer), fixed by QOG_RECONNECT_FIRST.
- Episode 1 on the board (Agent AC, not run on hardware): the data moved to 0x10100000 on the display and 0x10200000 on main, so start and all of episode 1 fit both chips (13.19 of 14.94 MB, 5.75 of 6 MB). The server stack went from 35 to 21 KB (measured worst 11.0 KB in board bytes, a bound of about 16.4 KB with the deepest hull recursion of e1m3), the server hunk from 160 to 174 KB, and every episode 1 script with sound runs in it. The edge fallback no longer stops the game. Episodes 2 and 3 also fit the display's region one at a time (episode 4 does not), main's 6 MB hold one episode.
- Episodes 2 and 3 on the board (Agent AG, not run on hardware): one app runs any episode's image. mkboard writes the start level into the image (`qogboot.txt`, start when the image has it) and the board client runs `qog_boot` instead of `map e1m1` (images without the file, like today's episode 1, still start in e1m1). Both images keep start (13.98 and 13.17 MB of 14.94 on the display, 5.97 and 5.96 of 6 MB on main). A level exit or a save of a level the image does not hold no longer stops the game: the exit goes to the image's start level with a new player's items, the save is not loaded. The load's 8 KB line buffer moved from the server hunk to the stack (`QOG_LOADGAME_STACKBUF`), 7 to 8 KB less on every level: worst e2m7 172 KB of 174, e1m3 163. Server stack measured worst 13.3 KB of 21 (e3m5's 111-level hull recursion), constructed worst 18.1 KB on e3m5.
- 300 MHz and the profiler (Agent AN, not run on hardware): both apps run 300 MHz at 1.25 V with the flash at 150 MHz when every check passes (div 2, the middle passing RX delay of 1 to 3), else 75 MHz. Each prints `[quake] temp` every 5 s. Step back with `-DQOG_SYS_KHZ=250000 -DQOG_SYS_MV=1200`, or keep the flash at its rating with `-DQOG_FLASH_MAX_KHZ=133000`. `-DQOG_PROF=ON` (in its own build folder) prints each core's top 20 functions every 5 s, and `tools/prof_resolve.py` adds them up from a saved log (docs/changes.md).
- PIO scanout (Agent AP, not run on hardware): core 1 sends the LCD pixels through a PIO state machine (pio1) at 60 MHz at 300 MHz (300 / 5) with no gap between pixels, where the PL022 gave 50 MHz and gaps, so a scanout takes about 17.2 ms instead of 22.4 (13.0 instead of 17.0 with the status bar skipped). The PL022 still sends the window commands. In Turbo, characters over the packed view (demo3's notify lines) are drawn by the scanout instead of spreading the view. The PC model puts demo3's race wait at about 1.7 ms instead of 5.7 in Fast and 1.5 instead of 5.6 in Turbo. The boot log says `[qog_video] lcd pio1 sm 0, 60000 kHz ...`, the status bar diag line ends with `last scan <us> us for <rows> rows`. Fallback `-DQOG_LCD_PIO=OFF`, a slower PIO `-DQOG_LCD_PIO_KHZ=50000` (docs/changes.md).
- Race package (Agent AP, not run on hardware): the notify clear the 3D view draws over is skipped (it waited for the whole scanout in 898 of 1,094 demo3 frames), the brush entities run before the wait for the end of the scanout, and a scanout that sends the status bar sends those rows first (`QOG_BOARD_HUDFIRST`, on), all exact. boardbench puts demo3 at 27.8 fps in Fast (26.1 on main) and 34.7 in Turbo (30.0). In Turbo the status bar goes to the LCD at most every `r_hudcap` ms (100, `QOG_BOARD_HUDCAP`, approved by the user). Two packed Turbo views do not fit (docs/changes.md).
- Sound (agent-w, not yet heard on the board): id's mixer runs on main for the display's sound calls, the display plays the samples on the I2S amplifier by PIO and DMA. Main's data image must carry the sounds (`mkboard.py --main`), the client stack is 32 KB with sound. Exact on the PC. Agent K's exact edge fallback runs when the stack holds its table, else (Agent AC) the waiting spans are drawn without z for that one view, never a stop.

## Board speed predicted on the PC (Agent AS, tools/boardbench.ps1)
- `powershell -File tools\boardbench.ps1` in any worktree that has the paks in `data\id1` and the `third_party` junction. It builds quakeog_pc with the board client's render flags and the cost model's work counts in its own folder (`build-boardbench`, `-DQOG_PC_BOARDMODEL=ON`), plays timedemo demo3 in Fast and in Turbo hidden and silent through tools/pctest.ps1, and prints the board ms per phase, the scanout waits and the predicted demo3 fps with a 10 to 90% range, at 300 MHz with the LCD by PIO at 60 MHz (Agent AP), `-Lcd pl022 -Spi 50` for the SPI peripheral, `-Mhz 250 -Spi 62.5 -Lcd pl022` for the old clock. The last lines read `BOARDBENCH Fast fps ...` and `BOARDBENCH Turbo fps ...`. About 3 minutes the first time, 1 minute after.
- `-Ref agent-xx` measures another branch: a temporary worktree next to this one (short path, the engine's paths are at most 128 characters), this tool merged in when the branch lacks it, removed afterwards. `-WhatIf "label=item,item;label=item"` asks the model what changes would give (several separated by `;`): `nonotify` (notify text no longer waits for the whole scanout), `noedgetable` (the edge table clear of the status bar rows), `norace` (no scanout waits at all), `early:bmodels` (a phase moved before the wait for the scanout's end), `spans*0.7` (a phase that much cheaper), `nopipe` (without Agent AM's two-core surfaces).
- Scoreboard, calibration and ranked attacks: docs/fps-board.md. The board measured f7d9450 at 20.0 fps in Fast and 22.3 in Turbo, and the model is now calibrated on that run (tools/boardmodel_calib.json, made by `python tools\boardmodel.py calibrate-board --calib tools\boardmodel_calib_de58316.json --log tools\boardmodel_f7d9450_fast.csv.gz -o tools\boardmodel_calib.json`, board numbers in `BOARD_F7`): f7d9450 gives 20.0 and 22.8. `hudcap:10` in `-WhatIf` is the approved Turbo status bar cap.
- How it works: port/pc/boardmodel_pc.c writes one line of work counts per timedemo frame (`-bmlog`), every count named by the code path that did the work (engine/qog_bmodel.h, QOG_LMAP_STATS, QOG_ALIAS_STATS, QOG_PHASE_XIP). tools/boardmodel.py gives each path float calls and integer cycles, two factors fitted to the board's de58316 phases plus a residual per phase, and simulates each frame in board time with the LCD scanout's row waits, the wait after R_RenderWorld and notify text. A branch that makes the same work cheaper without changing any count (a faster loop over the same pixels) is invisible to it: add a `QOG_BM_` count for the new path and give it weights in `WEIGHTS`.
- New board numbers: put them in `BOARD_REF` (or `BOARD_E1M1`) in tools/boardmodel.py, log the measured commit with `-DQOG_PC_BOARDMODEL=ON` (the de58316 reference is main with Agent AL's six flags, Agent AQ's eight and `QOG_DRAW_CORE1` taken out by `-DQOG_PC_REMOVE_DEFS`, whose counts equal an untouched de58316 build's within 0.3%), gzip the log over `tools/boardmodel_ref.csv.gz`, then `python tools\boardmodel.py calibrate --log tools\boardmodel_ref.csv.gz --e1m1 tools\boardmodel_ref_e1m1.csv.gz -o tools\boardmodel_calib.json`.

## Flashing the split game with episode 1 (Agent AC's flash map, one CPU in BOOTSEL at a time)
The flash map moved (platform/qog_flashmap.h): display data at 0x10100000 (app slot 913,408 B, data 14.94 MB up to the save slots), main's server data at 0x10200000 (app slot 2 MB, data 6 MB up to the FAT volume at 8 MB). The display bootloader's 128 KB and main's FAT volume are not touched. Both apps fail their build when they outgrow their slot. Data written for the old map is not found by the new apps and the other way round, so both images must be written again. Run from the repo root.
1. Images, start and all of episode 1 (13.19 MB display, 5.75 MB main): `python tools\mkboard.py --pak data\id1\pak0.pak --pak data\id1\pak1.pak --manifests build-pc-dev\manifests --maps start e1m1 e1m2 e1m3 e1m4 e1m5 e1m6 e1m7 e1m8 --exe build-pc-dev\Release\quakeog_pc.exe --stub-maps --main --display-no-sounds --display-no-progs --demos -o build-board\qb_ep1` (Agent AF: `--demos` keeps demo1 to demo3 for the Benchmark menu line, the display image grows to 13.69 MB and main's image is byte identical) (the PC build must include agent-ac, it maps its packs at the new address. Agent AC's run left `build-board\qb_ep1.uf2` and `build-board\qb_ep1_main.uf2` ready). The PC's own `data\id1\qogbake.bin` was baked for 0x10400000 and is now skipped with a message: run `qog_bake` once (`quakeog_pc -nosound -nobake +qog_bake +qog_quit` through tools/pctest.ps1) to use it again.
2. Build with every option given, the build folder keeps old values: `cmake --preset target -DQOG_SPLIT=ON -DQOG_AOT=ON -DQOG_AOT_PAK=<full path to data\id1\pak0.pak> -DQOG_SPLIT_MAIN_EMBED=quake_display -DQOG_SOUND=ON -DQOG_CL_HUNK_KB=75 -DQOG_CL_STACK_KB=32 -DQOG_SV_HUNK_KB=174 -DQOG_SV_STACK_KB=21 -DQOG_SYS_KHZ=300000 -DQOG_SYS_MV=1250 -DQOG_FLASH_FAST=ON -DQOG_FAT_FORMAT_IF_MISSING=ON`, then `cmake --build build --target quake_main`. It prints `qog: app quake_display.bin is ... of the 913408-byte app slot` and `qog: app quake_main.bin is ... of the 2097152-byte app slot`.
3. With the old game still running on both chips: `python third_party\wiliOGbsp\tools\fw.py bootsel --cpu display`, then copy `build-board\qb_ep1.uf2` to the RPI-RP2 drive. The ROM writes 0x10100000 to 0x10E30BF0 only, below it the bootloader, the app metadata and the app (at most 0x100000) keep their bytes. The display then restarts into its bootloader, which starts an app only when main sends RUN, and the old main app, waiting on the link in mid-game, sends none, so the old display app never runs against the new data. Main keeps waiting without a reset (the link wait kicks the watchdog). Do this step first: later on main restarts every 20 s or so until its data is written, and each restart resets the display, which would break a copy of 13 MB.
4. `python third_party\wiliOGbsp\tools\fw.py flash quake --uf2 build\apps\quake\quake_main.uf2`. Main restarts, its display update sends the new display app (364 KB, the bootloader erases only the sectors it needs, below 0x100000) and RUN, and the new display app finds its data. The new main app finds no server data at 0x10200000 yet and stops with `Sys_Error` (USB stays up for 20 s, then the watchdog restarts both chips, again and again). Nothing is written to flash in that loop.
5. `python third_party\wiliOGbsp\tools\fw.py flash quake --uf2 build-board\qb_ep1_main.uf2` (the touch reaches main during one of its 20 s reports, else fw.py asks for BOOTSEL by hand and waits). It writes 0x10200000 to 0x107BFFFF only: the app below 2 MB and the FAT volume with the saves keep their bytes. Main restarts, the display update finds the display app current and sends RUN, and both chips start episode 1 (`QOG_BOARD_MAP` e1m1).
6. On COM8 the display's diag line now ends with `zedge <n> noz <m>`: edge fallbacks that moved the edges to the stack, and those drawn without z (Agent AC, a one-frame glitch where models show through the world in some rows, never a stop). On COM7 main's `stack free` counts above the sound's 6 KB, of 21 KB.
Never flash the stand-in display image as the game. Never UF2-copy a display application (lessons L4). Data UF2s are fine.

## Installing one episode (Agent AG, images with qogboot.txt, any of episodes 1 to 3)
The app built with this branch (QOG_BOARD_BOOT on by default) starts the level the data image names, so changing episodes needs only the two data images. Episode 4 does not fit either region. Run from the repo root.
1. Images (episode 2, the same with e3m1 to e3m7 for episode 3, and start e1m1 to e1m8 for episode 1): `python tools\mkboard.py --pak data\id1\pak0.pak --pak data\id1\pak1.pak --manifests <manifests of every level> --maps start e2m1 e2m2 e2m3 e2m4 e2m5 e2m6 e2m7 --exe build-pc-dev\Release\quakeog_pc.exe --stub-maps --main --display-no-sounds --display-no-progs -o build-board\qb_ep2`. The manifests of episodes 2 to 4 are in Agent Y's `qog-wt-y\build-y\manifests` (33 files, the episode 1 ones are the same as build-pc-dev's). `--boot-map e2m1` starts the image in the episode's first level instead of start. Leave `--demos` out: the Benchmark's demo3 plays e1m6, which only episode 1's image holds, and on another image it would end the game. Agent AG left `build-board\qb_ep2.uf2`, `qb_ep2_main.uf2`, `qb_ep3.uf2` and `qb_ep3_main.uf2` ready.
2. `powershell -File tools\install_episode.ps1 -Episode 2` does the three steps of the episode 1 section (display data by `fw.py bootsel --cpu display` and a copy, then the app, then main's data), each tried three times, and stops whenever two RPI-RP2 drives are mounted. `-SkipApp` leaves the app as it is (an episode change once the app is current), `-Print` only shows the steps. Without the script, run steps 3 to 5 of the episode 1 section with `qb_ep2.uf2` and `qb_ep2_main.uf2`.
3. The saves on main's volume stay. A save of a level the new image does not hold is not loaded ("That save's level is not in this data image"), the game goes on.

## Housekeeping
- Push with GitHub Desktop or `git push`. Silent pushes fail on authentication.
- Remove finished worktrees (qog-wt-b to qog-wt-u and qog-wt-fly) and their branches: unlink each `third_party` junction first with `cmd /c rmdir`, then `git worktree remove`, then `git branch -d`.
- Rules: tests always go through tools/pctest.ps1 (hidden, `-nosound`, `-basedir`). Commits have a one-line title, bullet body, no colons, semicolons or em dashes, no mention of any AI.
- Game data (data/id1, qogbake.bin, any board image) is never committed.

## Still open (nothing was done on it)
- Server hunk (Agent AG): e2m7 with sound needs 172 of 174 KB. More room would come from edicts taken in blocks as the level uses them (exact, e2m7 never uses 85 of its 438 edicts of 208 B) or a smaller `QOG_EDICT_MARGIN_BOARD` (a behaviour change). The PC split pair's server half crashes on e2m3 when its data folder has no qogbake.bin (a NULL r_notexture_mip on the server half, docs/changes.md), the board is not affected.
- Client hunk: closed for the whole game by Agent AD (75 KB). e4m5 and e4m8 have teleporters aimed at an info_null, a Host_Error in id's game too.
- Next steps, from the measurements: build a base, a depth and a split pair build, measure `qog_mem hunk` per map on the split client, then cut the biggest blocks exactly. Candidates are the 7.5 KB net_message in the z-buffer temp region during signon, the per-level map arrays (about 35 KB on E1M1) and the model_t RAM table. The 4 KB console and command buffer cuts change behaviour, so they need the user's decision.
- The 1-byte depth buffer reaches the edge fallback in a few views per episode (4 in the episode 1 fight tour). On the board those now draw without z when the stack is short (a few models or particles show through the world in some rows for one frame). Why the edges and spans meet there is still not looked at.
- Sound: listen on the board, and raise `_snd_mixahead` (0.1, at most 0.18) if it breaks up. The display's flash image still holds sounds the client no longer opens (about 1.6 MB to win for maps).
